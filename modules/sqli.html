🧪 SQL-Injection-Simulation
i
Grundidee: eine Webseite baut oft einen Datenbank-Befehl aus deiner Eingabe zusammen. Tippst du statt eines normalen Namens etwas mit Anführungszeichen/Sonderzeichen ein, kannst du diesen Befehl "umbiegen" - genau das simulieren wir hier, ganz ohne echte Datenbank.

Dies ist eine reine Lernsimulation ohne echte Datenbank oder Codeausführung. Beide Formulare unten arbeiten ausschliesslich gegen ein hartcodiertes JavaScript-Array im Browser. Es gibt keinen Server, keine echte SQL-Engine und keine echte Ausführung deiner Eingaben. Die "Injection" wird durch einfache Mustererkennung (RegEx) nachgebildet, rein zur Veranschaulichung des Prinzips.
Modul abgeschlossen! Du hast das Prinzip in beiden Varianten ausprobiert.

Checkliste

⬜ Injection im unsicheren Formular auslösen
⬜ Gleiche Eingabe im parametrisierten Formular testen
⬜ Alle Herausforderungen lösen (0 / 3)

Beispiel-Payloads (zum Ausprobieren)

Klick auf einen Button, um Benutzername/Passwort im unteren, unsicheren Formular automatisch zu befüllen.

🔓 Teil 1: Unsicherer Login (String-Verkettung)

Diese Variante baut den "Query-Text" per String-Verkettung zusammen - genau das Muster, das echte SQL-Injection in der realen Welt ermöglicht.

Simulierter Query-Text:

SELECT * FROM users WHERE username = '' AND password = '';

🔒 Teil 2: Sicherer Login (parametrisiert)

Diese Variante behandelt Eingaben als reine Daten (gebundene Parameter), die niemals in den Query-Text eingemischt werden.

Simulierte parametrisierte Query:

SELECT * FROM users WHERE username = ? AND password = ?;

Warum funktioniert das eine, aber nicht das andere?

Im unsicheren Formular wird die Eingabe direkt in den Text der Abfrage eingesetzt. Enthält die Eingabe ein Anführungszeichen ', kann sie den String vorzeitig "abschliessen" und eigenen SQL-Code anfügen - z.B. eine immer wahre Bedingung (' OR '1'='1) oder einen Kommentar (--), der den Rest der echten Abfrage (inkl. Passwort-Prüfung) unwirksam macht.

Im sicheren Formular wird die Struktur der Abfrage (WHERE username = ? AND password = ?) fest vorgegeben. Die Eingaben werden erst danach als reine Werte ("gebundene Parameter") übergeben. Sie können die Struktur der Abfrage nicht mehr verändern - ein Anführungszeichen ist dann einfach ein Anführungszeichen im Passwort, nicht Teil des SQL-Codes.

In echten Anwendungen heisst diese Technik Prepared Statements / parametrisierte Queries und ist der Standard-Schutz gegen SQL-Injection - unabhängig von der Programmiersprache.
