🖥️ Configuration Manager (SCCM)
i
Was früher "SCCM" (System Center Configuration Manager) hiess, heisst heute offiziell "Microsoft Configuration Manager" - im Alltag sagen die meisten Admins trotzdem weiterhin einfach "SCCM" oder "ConfigMgr".

Wie On-Premises-Softwareverteilung im grossen Massstab funktioniert: Collections, Applications mit Erkennungsregeln, Deployments (Erforderlich vs. Verfügbar) und automatisiertes Windows-Update-Management über den Software Update Point.

Was ist Configuration Manager?
i
GPOs (siehe Modul Active Directory) können Software verteilen, aber ziemlich grob: keine Erkennung, ob etwas schon installiert ist, kaum Reporting, kein Rollout in Wellen. Configuration Manager ist die Antwort darauf, wenn eine Firma das im grossen Massstab, nachvollziehbar und mit Kontrolle über Bandbreite und Zeitpunkt tun will.

Configuration Manager (früher SCCM) ist eine On-Premises-Lösung, um tausende Windows-Geräte zentral zu verwalten: Software verteilen, Betriebssystem-Images ausrollen, Compliance durchsetzen und Windows-Updates steuern. Ergänzt (und lässt sich per Co-Management kombinieren mit) Intune für cloud-verwaltete Geräte.

RolleAufgabe
Site-ServerZentrale Verwaltungskomponente, auf der Configuration Manager selbst läuft
SQL-Server (Standortdatenbank)Speichert sämtliche Konfiguration, Inventar- und Complianceberichte
Management PointVermittelt zwischen Clients und Site-Server (Richtlinien abholen, Status melden)
Distribution PointStellt die eigentlichen Installationsdateien (Content) für Clients bereit
Software Update PointSteuert Windows-Updates - technisch auf WSUS aufbauend (siehe unten)

Voraussetzung ist immer eine funktionierende Active-Directory-Domäne - Clients werden über die Domänenmitgliedschaft erkannt und adressiert, ganz ähnlich wie bei GPOs.

Collections: wer bekommt was?
i
Wie eine Gästeliste, die sich teils manuell pflegen lässt, teils sich automatisch aktualisiert: "alle mit Nachname Meier" würde sich von selbst anpassen, sobald jemand hinzukommt oder wegzieht.

Eine Collection ist eine Gruppe von Geräten oder Benutzern - das Ziel jeder Bereitstellung (Deployment). Es gibt zwei Arten der Mitgliedschaft:

Direkte MitgliedschaftAbfragebasierte (dynamische) Mitgliedschaft
Pflegemanuell einzeln hinzufügenWQL-Abfrage, aktualisiert sich automatisch
Beispiel"genau diese 5 Testgeräte""alle Geräte mit Windows 11" oder "alle Geräte in OU Support"
Typischer EinsatzPilotgruppen, Ausnahmengrosse, sich verändernde Zielgruppen

Eingebaute Standard-Collections wie Alle Systeme und Alle Benutzer existieren immer - eigene Collections werden meist als Unterordner/Teilmenge davon angelegt, um gezielter ausrollen zu können.

Applications & Deployment Types
i
Eine Erkennungsregel ist wie ein Türsteher, der VOR dem Installieren erst nachschaut, ob die Person nicht schon drin ist - ohne sie würde Configuration Manager bei jedem Zyklus versuchen, dieselbe Software erneut zu installieren.

Eine Application ist das moderne Bereitstellungsobjekt (Nachfolger der älteren, einfacheren Packages) - sie kann mehrere Deployment Types enthalten, z.B. eine MSI-Variante für Windows 11 und eine andere für ältere Geräte.

BestandteilZweck
Erkennungsregel (Detection Rule)Prüft VOR der Installation, ob die App schon vorhanden ist (z.B. MSI-Produktcode, Datei- oder Registry-Prüfung) - verhindert unnötige Neuinstallationen
Anforderungen (Requirements)Bedingungen, die erfüllt sein müssen (z.B. Betriebssystemversion, freier Speicherplatz)
Abhängigkeiten (Dependencies)Andere Applications, die vorher installiert sein müssen
RückgabecodesWelche Exitcodes als Erfolg gelten (identisches Konzept wie im Modul Software-Paketierung)

Deployments: Erforderlich vs. Verfügbar
i
Genau dasselbe Prinzip wie bei GPO-Softwareinstallation ("Zugewiesen" vs. "Veröffentlicht") - nur mit deutlich mehr Kontrolle: Zeitfenster, Erkennungsregeln, Compliance-Reporting.

Ein Deployment verknüpft eine Application (oder ein Software-Update) mit einer Collection und legt fest, WIE sie ankommt:

Erforderlich (Required)Verfügbar (Available)
Installationautomatisch, bis zur Deadline erzwungenNutzer installiert freiwillig über Software Center
Vergleichbar mit GPO"Zugewiesen" (Assigned)"Veröffentlicht" (Published)
Typischer EinsatzSicherheits-relevante Pflichtsoftwareoptionale Werkzeuge, Self-Service

Der grosse Unterschied zu GPO-Softwareinstallation: Deployments lassen sich zeitversetzt in Wellen (Ringen) ausrollen, mit Wartungsfenstern koppeln und liefern detailliertes Compliance-Reporting - GPO kennt nur "installiert beim nächsten Neustart", ohne Rückmeldung.

Windows-Updates verwalten (Software Update Point)
i
Ringe beim Patchen sind wie ein Testesser vor einem grossen Bankett: eine kleine Gruppe (Pilot-Ring) bekommt das Update zuerst - erst wenn dort nichts kaputtgeht, folgen die restlichen, grösseren Ringe.

Der Software Update Point baut technisch auf WSUS (Windows Server Update Services) auf, wird aber komplett über Configuration Manager gesteuert:

  • Software Update Groups: ein kuratiertes Bündel von Updates (z.B. "Patchday September 2026"), das gemeinsam bereitgestellt wird.
  • Automatic Deployment Rules (ADRs): Regeln, die neue Updates automatisch nach Kriterien (z.B. "Kritisch/Sicherheit, Windows 11, monatlich") erfassen und bereitstellen - ohne jeden Patchday manuell nachzupflegen.
  • Wartungsfenster (Maintenance Windows): schränken pro Collection ein, WANN Updates/Neustarts überhaupt stattfinden dürfen (z.B. nur nachts).
  • Ring-basiertes Ausrollen: dieselbe ADR/Update-Gruppe wird zuerst an eine kleine Pilot-Collection deployt, erst nach Beobachtungszeit an breitere Collections - reduziert das Risiko, dass ein fehlerhaftes Update sofort alle Geräte trifft.

🖥️ Praxislabor Teil 5: 7-Zip über Configuration Manager statt GPO verteilen
i
Dieselbe Aufgabe wie im Paketierungs-Labor (7-Zip an CL01 bringen) - diesmal aber über Configuration Manager statt GPO, zum direkten Vergleich: Erkennungsregel, Collection und Deployment statt Freigabe und GPO-Verknüpfung.

Baut auf allen bisherigen Laboren auf (SRV01 als Domänencontroller mit DHCP/DNS/AD DS/AD CS, CL01 in der OU Support). Configuration Manager ist deutlich schwergewichtiger als die bisherigen Rollen - realistisch ca. 2-4 Stunden zusätzlich, inkl. SQL-Server-Installation. Zwei Wege stehen offen:

Weg A (empfohlen für den Einstieg): vorkonfiguriertes Evaluation Lab Kit

Microsoft stellt ein selbstinstallierendes Laborpaket bereit: automatisch bereitgestellte VMs inkl. Domänencontroller, Client und fertig eingerichtetem Configuration Manager. Deutlich schneller als der manuelle Weg B, allerdings eine EIGENE, abgeschottete Laborumgebung (nicht direkt SRV01/CL01) - gut geeignet, um die Konzepte oben zuerst gefahrlos auszuprobieren.

  • Lab Kit Microsoft Intune and Configuration Manager Evaluation Lab Kit (kostenlos, inkl. Schritt-für-Schritt-Laborhandbuch)

Weg B (aufbauend, wie die bisherigen Labore): manuell auf SRV01 installieren

  1. Voraussetzung: SQL Server auf SRV01 installieren (kostenlose Express-Edition reicht für ein Labor). Download: SQL Server Downloads (Microsoft)
  2. Configuration Manager (Current Branch) herunterladen und installieren - Standort als eigenständigen Primärstandort einrichten. Download: Microsoft Configuration Manager Evaluation · Anleitung: Microsoft Learn - Configuration Manager-Lab einrichten
  3. Distribution Point und Management Point auf SRV01 aktivieren (Standardrollen bei einer Primärstandort-Installation).
  4. CL01 als Client registrieren (Client-Push oder manuelle Installation von ccmsetup.exe).
  5. Eine Collection anlegen (Abfragebasiert: alle Geräte in der OU Support - dieselbe OU wie im Edge-GPO-Beispiel).
  6. Eine Application für 7-Zip anlegen (dieselbe .msi wie im Paketierungs-Labor), Erkennungsregel auf den MSI-Produktcode setzen.
  7. Deployment erstellen: Application → neue Collection, Zweck Erforderlich, Deadline setzen.
  8. Auf CL01 einen Richtlinienabruf auslösen (Software Center → Einstellungen → "Richtlinien jetzt aktualisieren" oder Invoke-CMClientAction auf SRV01), danach im Software Center auf CL01 prüfen, ob 7-Zip installiert wurde.
Vergleich zum GPO-Labor: Beide Wege installieren am Ende dieselbe .msi auf demselben Client - der Unterschied liegt in Kontrolle und Sichtbarkeit: Configuration Manager weiss (per Erkennungsregel und Reporting) genau, ob die Installation geklappt hat, ein GPO-Deployment liefert dazu keine Rückmeldung.
