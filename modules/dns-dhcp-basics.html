🧭 DNS-Auflösung & DHCP-Prozess im Detail

Wie eine Anfrage nach einer Adresse tatsächlich Schritt für Schritt durch die DNS-Hierarchie läuft, und wie ein Client bei DHCP überhaupt an seine IP-Konfiguration kommt - die Mechanik hinter den Modulen "DNS-Konzepte" und "DHCP/DNS-Tickets".

Der DHCP-Prozess: DORA + Erneuerung
i
Wie eine Wohnungssuche: du rufst laut in die Nachbarschaft, wer eine Wohnung frei hat (Discover), mehrere Vermieter melden sich mit einem Angebot (Offer), du entscheidest dich für eines und sagst das öffentlich allen (Request - damit die anderen ihre Wohnung nicht länger für dich freihalten), der gewählte Vermieter bestätigt (Acknowledge).

Bevor ein Gerät überhaupt eine IP-Adresse hat, kann es niemanden gezielt ansprechen - deshalb läuft der Adressbezug per DHCP über Broadcasts, nach dem klassischen DORA-Schema:

💻
Client
🖥️
DHCP-Server 1
🖥️
DHCP-Server 2
  1. 1. DISCOVERClient sucht per Broadcast nach verfügbaren DHCP-Servern.
  2. 2. OFFERJeder erreichte Server bietet eine freie IP-Adresse samt Konfiguration an.
  3. 3. REQUESTClient entscheidet sich für ein Angebot und fordert es per Broadcast an - so sehen auch die anderen Server die Entscheidung.
  4. 4. ACKDer gewählte Server bestätigt - die Adresse ist vergeben, der andere Server gibt sein Angebot wieder frei.

Bereit - klicke "Abspielen" oder gehe Schritt für Schritt durch.

Praktische Konsequenz: läuft ipconfig /release gefolgt von ipconfig /renew - das ist der klassische erste Trick bei IP-Problemen - startet genau dieser DORA-Prozess von vorne.

DNS-Auflösung Schritt für Schritt (rekursiv)
i
Wie eine Telefonauskunft-Kette: du rufst eine zentrale Auskunft an (Resolver), die weiss deine Nummer nicht, verweist dich aber an die richtige Landesauskunft (TLD), die wiederum an die zuständige Firmenzentrale (autoritativer Server) verweist - am Ende bekommst DU die Antwort trotzdem nur einmal, von deiner ersten Anlaufstelle.

Kein einzelner Server kennt jede Domain der Welt - die Auflösung läuft stattdessen als Kette von Verweisen ("Referrals") durch die DNS-Hierarchie:

💻
Client
📇
Rekursiver Resolver
🌐
Root-Server
🏷️
.ch TLD-Server
🏢
Autoritativer NS (beispiel.ch)
  1. 1.Client fragt seinen Resolver: "Wie lautet die IP von shop.beispiel.ch?"
  2. 2.Nichts im Cache - Resolver fragt einen Root-Nameserver.
  3. 3.Root-Server kennt die Domain nicht, verweist aber auf den zuständigen .ch-TLD-Server.
  4. 4.Resolver fragt den .ch-TLD-Server.
  5. 5.TLD-Server verweist weiter auf den autoritativen Nameserver von beispiel.ch.
  6. 6.Resolver fragt den autoritativen Nameserver direkt.
  7. 7.Autoritativer Server kennt die Antwort: die IP-Adresse von shop.beispiel.ch.
  8. 8.Resolver cacht das Ergebnis (für die Dauer der TTL) und gibt die Antwort an den Client zurück.

Bereit - klicke "Abspielen" oder gehe Schritt für Schritt durch.

Der (lokale/rekursive) Resolver merkt sich das Ergebnis danach für die Dauer der TTL im Cache - erst wenn diese abläuft, wird die komplette Kette bei Bedarf erneut durchlaufen (siehe Modul "DNS-Konzepte" zu TTL/Propagation).

DNS-Record-Typen im Überblick

TypBedeutung
AOrdnet einen Domainnamen einer IPv4-Adresse zu
AAAAOrdnet einen Domainnamen einer IPv6-Adresse zu
CNAMEVerweist auf einen anderen (kanonischen) Domainnamen statt auf eine IP
MXLegt fest, welcher Mailserver für die Domain E-Mails entgegennimmt
PTRReverse-DNS: ordnet einer IP-Adresse einen Domainnamen zu (umgekehrte Richtung von A)
NSNennt den/die zuständigen (autoritativen) Nameserver für eine Domain
SOAStart of Authority - administrative Basisdaten der Zone (u.a. Seriennummer, Refresh-/Retry-Intervalle)
TXTBeliebiger Text-Eintrag, z.B. für SPF/DKIM/DMARC oder Domain-Verifizierung

SPF/DKIM/DMARC (alle als TXT-Records hinterlegt) werden ausführlich im Modul E-Mail-Sicherheit behandelt.

🖥️ Praxislabor Teil 1: eigene DHCP/DNS-Testumgebung mit VMs aufbauen
i
Die Animationen oben zeigen, WAS passiert - hier baust du eine echte, kleine Testumgebung, um es selbst zu erleben: dein eigener DHCP-Server vergibt eine IP an einen echten (virtuellen) Client, dein eigener DNS-Server beantwortet eine echte Anfrage.

Anders als die Animationen oben läuft dieses Labor NICHT im Browser - du baust es in echten virtuellen Maschinen (VMs) nach. Rechne mit ca. 1-2 Stunden (inkl. Downloads/Installation). Ziel: ein Windows-Client bezieht seine IP-Konfiguration automatisch von einem selbst eingerichteten DHCP-Server und löst einen selbst angelegten DNS-Eintrag auf. Dieser Server wird im Modul Active Directory im Praxislabor Teil 2 direkt weiterverwendet (Beförderung zum Domänencontroller) - also nicht gleich wieder löschen. Das Labor wächst über mehrere Module hinweg auf derselben Umgebung weiter (siehe Praxislabor-Karte jeweils am Ende der aufbauenden Module) - nicht bei jedem Modul neu von vorne beginnen.

Voraussetzungen & Downloads

  • Virtualisierung Oracle VirtualBox (kostenlos, Windows/Mac/Linux) - oder alternativ das in Windows Pro/Enterprise/Education bereits eingebaute Hyper-V (nur aktivieren, kein Download nötig).
  • Server-ISO Windows Server 2025 Evaluation (Microsoft Evaluation Center, 180 Tage kostenlos nutzbar - nur für Test-/Lernzwecke, nicht produktiv einsetzen).
  • Client-ISO Windows 11 Enterprise Evaluation (ebenfalls Microsoft Evaluation Center, 90 Tage kostenlos).
  • Hardware Empfehlung: mind. 8 GB RAM frei (beide VMs gleichzeitig laufen lassen), ca. 60 GB freier Speicherplatz.

Schritt für Schritt

  1. Virtualisierungssoftware installieren, zwei VMs anlegen: SRV01 (Windows Server) und CL01 (Windows 11).
  2. Beide VMs an dasselbe interne/private Netzwerk hängen (VirtualBox: "Internes Netzwerk", Hyper-V: "Privater virtueller Switch") - nicht NAT, sonst sehen sich die beiden VMs gegenseitig nicht.
  3. Windows Server auf SRV01 installieren (Desktop Experience, nicht Server Core - einfacher für den Einstieg), danach eine statische IP setzen, z.B. 192.168.100.10 / 255.255.255.0.
  4. Auf SRV01 die DHCP-Serverrolle installieren und einen Scope einrichten (z.B. Bereich 192.168.100.100-200, Gateway und DNS-Server = die eigene Server-IP 192.168.100.10). Anleitung: Microsoft Learn - DHCP-Server installieren
  5. Auf SRV01 die DNS-Serverrolle installieren, eine Forward-Lookup-Zone anlegen (z.B. lab.local) und einen Testeintrag ergänzen (z.B. A-Record server1.lab.local → 192.168.100.10). Anleitung: Microsoft Learn - DNS-Server installieren
  6. Windows 11 auf CL01 installieren (Netzwerkadapter bleibt auf Standard = "IP automatisch beziehen").
  7. Verifizieren auf CL01: ipconfig /all (hat der Client eine Adresse aus 192.168.100.100-200 samt korrektem DNS-Server bekommen?) und nslookup server1.lab.local (löst der eigene DNS-Server den Testeintrag auf?).
Wenn's nicht klappt: die häufigsten Ursachen sind das falsche Netzwerk (NAT statt intern/privat gewählt) oder eine aktive Windows-Firewall-Regel, die DHCP-Broadcasts blockiert - beides lässt sich gut mit dem Wissen aus dem Modul DHCP/DNS-Troubleshooting eingrenzen.
